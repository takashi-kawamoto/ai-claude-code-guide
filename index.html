CLAUDE CODE / CLAUDE.MD

Claude CodeのCLAUDE.md一覧

まず用意したいCLAUDE.md

ユーザー用CLAUDE.md

~/.claude/CLAUDE.md

記載例

  • # CLAUDE.md
回答は日本語で行う
Markdownで出力する
Mermaid図を積極的に利用する
コードにはコメントを書く
入力が曖昧な場合はAsk User Questionを利用する

使いどころ・ポイント

  • 全プロジェクトに共通する回答スタイルを書く
  • 毎回プロンプトに書いていた指示をまとめる

すべてのプロジェクトで読み込まれます。プロジェクト側にCLAUDE.mdがなくても影響するため、挙動がおかしいときは/memoryで確認してください。

プロジェクト用の基本テンプレート

CLAUDE.md

記載例

  • # プロジェクト概要（What）
React + TypeScriptによるWebアプリケーション

# 目的（Why）
業務効率化のための社内ツール

# 行動指針（How）
- 結論から回答する
- 前置きを書かない
- 不明点は推測せず確認する

# 検証方法
- コード変更後はテストを実行する
- Lintと型チェックを行う

# 完了条件
- テスト・Lint・型チェックがすべて成功している

使いどころ・ポイント

  • What・Why・Howの3つを軸に書く
  • 検証方法と完了条件を必ず入れる

特に重要なのはHowです。回答スタイル・作業ルール・使用ツール・禁止事項・出力ルールを書くと、AIの振る舞いが安定します。

開発プロジェクト用

CLAUDE.md

記載例

  • ## 技術スタック
Backend: Python / FastAPI
Frontend: React / TypeScript
Database: PostgreSQL

## 開発ルール
- 必ず既存設計を確認してから変更する
- 勝手にアーキテクチャ変更しない
- テストコードを必ず追加する

## 重要ドキュメント
Architecture: docs/architecture/
Requirements: docs/requirements/

使いどころ・ポイント

  • 技術スタックと重要ドキュメントの場所を明記
  • アーキテクチャ・コーディング規約・命名規則・テスト方針も候補

AIが一貫した実装を行えるよう、プロジェクト固有の前提を明文化します。

目次型CLAUDE.md

CLAUDE.md ＋ .claude/rules/

記載例

  • # CLAUDE.md
## 詳細ルール
- セキュリティ: .claude/rules/security.md
- コーディング規約: .claude/rules/coding-style.md
- アーキテクチャ: .claude/rules/architecture.md
## 作業手順
- .claude/skills/ 配下のSkillを使う

使いどころ・ポイント

  • 大規模案件で1つの巨大なCLAUDE.mdを作らない
  • CLAUDE.mdを「目次」、rules・skillsを「詳細仕様書」にする

必要なときだけ詳細を読ませる（Progressive Disclosure）ことで、コンテキストを節約できます。詳細ルールの例はRules一覧を参照してください。

ワークフローを制御するCLAUDE.md

AIレビューワークフロー用（司令塔型）

CLAUDE.md

記載例

  • # AI開発ワークフロー
## 基本方針
Claude Codeは実装担当とする。
Codexは独立レビュー担当とする。

## 開発工程
1. 要件を確認する。
2. coding Skillに従って実装する。
3. testing Skillに従ってテストする。
4. codex-review Skillに従ってCodexレビューを実施する。
5. 修正必須の指摘を修正し、テストを再実行する。

## 完了条件
- 必須テストが成功している
- Codexレビューを実施している
- Critical / High相当の未対応指摘がない

使いどころ・ポイント

  • 詳細なルール集ではなく、工程全体の司令塔として使う
  • 個々の手順はSkillsに分ける

レビューの手順は/codex:review --waitなどのコマンドで具体的に指定します。commit後の強制実行が必要になったらHooksを追加します。

定期実行用

CLAUDE.md

記載例

  • # Project Rules
## Code Review
レビュー時には以下を確認すること。
- バグ
- セキュリティ
- パフォーマンス
- 可読性
- テスト不足

## Report
レビュー結果はMarkdown形式で出力すること。
出力先: reports/

使いどころ・ポイント

  • cron・タスクスケジューラ・GitHub Actionsから起動する場合に使う
  • 起動側はclaude -p "定期コードレビューを実行してください"程度に短くできる

毎回巨大なプロンプトを書かずに済み、共通ルールを1か所で管理できます。

業務ワークスペース用のCLAUDE.md

ルート：フォルダの地図

workspace/CLAUDE.md

記載例

  • # フォルダの地図
- clients/ : 顧客ごとの情報
  取引先について聞かれたら、
  まず clients/index.md を読むこと
- mail/  : メールの下書き
- notes/ : メモ

ファイルを読む際はReadツールを使うこと

使いどころ・ポイント

  • 案件固有のルールは書かず、どこに何があるかだけを書く
  • 目次ファイル（index.md）へ誘導する

起動時に毎回読み込まれるため、太らせるとトークン消費が増え、精度も落ちます。オートモードではBashでファイルを読むとサブディレクトリのCLAUDE.mdが読まれないことがあるため、Readツールの使用を明記します。

サブディレクトリ：共通ルール

workspace/clients/CLAUDE.md

記載例

  • # 全顧客共通のルール
- 顧客情報は外部に出さない
- 返信文は提案にとどめ、送信は人間が行う
- 進捗は各顧客の profile.md に記録する

使いどころ・ポイント

  • そのフォルダを触るときだけ必要な前提を書く

配下のファイルを読んだタイミングで読み込まれ、上位階層のCLAUDE.mdも一緒に含まれます。

サブディレクトリ：顧客ごとの前提

workspace/clients/取引先A/CLAUDE.md

記載例

  • # 取引先Aの前提
- 担当者の呼び方: 〇〇様
- 文体: カジュアルで構わない
- これまでの経緯: profile.md を参照
- 禁止事項: 価格の提示は事前確認が必要

使いどころ・ポイント

  • 担当者の呼び方・会社の呼び方・取引条件・経緯・禁止事項を書く
  • 進捗や議事録の要約はprofile.mdに分ける

顧客ごとにトーンを切り替えられます。頻繁に更新される情報はCLAUDE.mdではなく別ファイルで管理します。

CLAUDE.mdの読み込みと書き方の基本

起動フォルダ直下のCLAUDE.mdは起動時に、サブディレクトリのCLAUDE.mdはそのフォルダのファイルを読んだタイミングで読み込まれます。ユーザー用（~/.claude/CLAUDE.md）とプロジェクト用は両方読み込まれるため、/memoryで内容を確認できます。毎回読み込まれるファイルは3,000〜5,000文字程度を目安に短く保ち、READMEのコピーではなくAI向けの指示だけを書きます。一度で完成させず、AIとのやり取りで気づいた点を少しずつ反映して育ててください。

機能や読み込みの仕様は変更される場合があります。最新の挙動は公式ドキュメントで確認してください。

プロジェクト概要（What・Why）

CLAUDE.md

書く内容（例）

  • 何のプロジェクトか（例：React + TypeScriptのWebアプリ）
  • 何のために存在するか（例：業務効率化のための社内ツール）

READMEは人向け、CLAUDE.mdはAI向けの指示書です。目的が違うので内容も分けます。

  • 不明点は推測せず確認する

書き方のポイント

  • 回答スタイル・作業ルール・使用ツール・禁止事項・出力ルールに分けて書く

What・Why・Howの中で特に重要なのがHowです。AIの回答スタイルや作業手順をそろえられます。

  • テーマ別の詳細は.claude/rules/へ分ける

.claude/rules/ に分けるルール

セキュリティルール

.claude/rules/security.md

書く内容（例）

  • 禁止：APIキー・パスワードをソースコードに書かない、個人情報をログに出さない
  • 禁止：.envを読まない、認証情報を表示しない、機密ファイルを編集しない
  • 必須：入力値の検証、SQLインジェクション対策、認証処理の共通化

書き方のポイント

  • 「禁止事項」と「必須対応」に分けて書く
  • AIに「セキュリティルールを追加して」と依頼して作らせることもできる

ルールだけでは止めきれない場合もあるため、許可設定・サンドボックス・Hooksと組み合わせて多重に守ります。

コーディング規約

.claude/rules/coding-style.md

書く内容（例）

  • 命名規則（クラス・関数・変数ごとの書き方）
  • コメント方針：複雑な処理には「何をするか」ではなく理由を書く

書き方のポイント

  • Bad例・Good例を並べて書く

具体例があると、AIが規約を誤解しにくくなります。

アーキテクチャルール

.claude/rules/architecture.md

書く内容（例）

  • 採用するアーキテクチャ（例：Clean Architecture）
  • レイヤー構成と依存の向き
  • 禁止：Domain層からのDBアクセス

書き方のポイント

  • 基本方針・構成・禁止事項の順に書く

やってはいけないことを明記しておくと、設計崩れを防げます。

テスト方針

.claude/rules/testing.md

書く内容（例）

  • 変更時は必ずテストを追加・更新する
  • 先にテストを書き、通るコードをAIに書かせる（TDD）
  • 修正後はテストを再実行する

書き方のポイント

  • 実行コマンドと合格条件を書いておく

セキュリティに関わる機能ほど、先にテストを書いておくと想定外の挙動に気づきやすくなります。

Git運用ルール

.claude/rules/git.md

書く内容（例）

  • mainブランチへの直接pushを禁止
  • 作業ブランチ → Pull Request → レビューの流れを守る
  • 破壊的なGit操作は実行前に確認する

書き方のポイント

  • ブランチ保護など、Git側の設定とあわせて運用する

「気づいたらmainが更新されていた」という失敗を防ぐためのルールです。

運用と安全のためのルール

環境・危険操作のルール

CLAUDE.md / rules

書く内容（例）

  • 本番と検証の接続先は、実行前に人間が確認する
  • データの削除・上書きなど破壊的な操作は実行前に確認を取る

書き方のポイント

  • 対象環境の切り替えをAI任せにしない

検証のつもりで本番環境に危険な処理をかけてしまう失敗が実際に起きています。止める仕組み（許可設定・サンドボックス）も事前に用意してください。

コンテキスト管理のルール

CLAUDE.md

書く内容（例）

  • タスクが終わったら/clearで履歴をクリアする
  • 作業内容をドキュメントにまとめてから再開する

書き方のポイント

  • 長いセッションを続けず、区切って作業する

コンテキストが増えすぎるとAIの判断精度が落ちる可能性があります。

  • 指摘への対応は必要最小限の変更にとどめる
  • 要件定義を最優先の参照元にする
  • 一定回数を超えたら人間にエスカレーションする

書き方のポイント

  • 指摘をそのまま直さず、仕様・コード・テストと照合してから修正させる

レビューの無限ループ、過剰なリファクタリング、仕様からの逸脱を防ぎます。

コスト・範囲の上限ルール

CLAUDE.md

書く内容（例）

  • やり取りの往復回数の上限
  • 「〇〇以内で作る」といったコスト・範囲の上限
  • キャッシュに載せられる情報は最初に読み込む

書き方のポイント

  • どこまで制約を書くかを、grill-meなどで詰めてから決める

ルールを削りすぎるとやり取りの往復が増え、かえってトークン消費が増えることがあります。

ルールの置き場所と書き方の基本

自分の開発スタイルは~/.claude/CLAUDE.md、システム概要や技術スタックはプロジェクトのCLAUDE.md、守るべき詳細なルールは.claude/rules/にテーマ別に置きます。CLAUDE.mdは毎回読み込まれるため、3,000〜5,000文字程度を目安に、必要な内容だけを短く書きます（Less is More）。詳細は別ファイルに分け、必要なときだけ読ませるようにします（Progressive Disclosure）。ルールは一度で完成させず、AIとのやり取りで気づいた点を少しずつ反映して育ててください。ルールは「お願い」なので、確実に止めたい操作はHooksや許可設定で強制します。

機能や設定方法は変更される場合があります。導入時には利用中のClaude Codeバージョンと公式ドキュメントを確認してください。

まとめた設定例

最初の一歩の設定

.claude/settings.json

設定例

  • {
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git log:*)"
    ],
    "ask": [
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(curl:*)",
      "WebFetch"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(rm -rf:*)",
      "Bash(git reset --hard:*)",
      "Bash(git push --force:*)"
    ]
  }
}

使いどころ・ポイント

  • 機密ファイルと破壊的なコマンドはdeny
  • Gitへの反映と外部通信はask
  • テスト・Lint・読み取り系のGitだけallow
  • 慣れてきたらallowを少しずつ増やす

テスト・Lintのコマンドはプロジェクトに合わせて書き換えてください。チームで共有する設定は.claude/settings.json、自分だけの設定は.claude/settings.local.jsonに書きます。

Permissions設定の基本

権限は~/.claude/settings.json（全プロジェクト）、.claude/settings.json（プロジェクトで共有）、.claude/settings.local.json（プロジェクトの自分用）のpermissionsに書きます。ルールが重なった場合はdeny → ask → allowの順に優先されるため、拒否したい操作は必ずdenyに入れます。現在のルールは/permissionsで確認できます。Claude Codeには危険な操作前の確認・危険コマンドの警告・サンドボックス・禁止ルールといった安全機能がありますが、100%安全になるわけではありません。権限は最初から広げすぎず、確実に止めたい操作はHooksやGitのブランチ保護とも組み合わせてください。

設定項目やルールの書き方は変更される場合があります。導入時には利用中のClaude Codeバージョンと公式ドキュメントを確認してください。
